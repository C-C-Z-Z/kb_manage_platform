- 文档版本：V1.1
- 文档状态：概要设计基线（组织账号与异常降级已实现）

- 需求依据：`知识库管理平台PRD.md`

### 0.1 阅读对象

- 产品负责人：确认架构是否覆盖 PRD 的业务闭环。
- 架构与研发负责人：据此完成技术选型、详细设计和模块拆分。

### 0.2 设计结论摘要

- 系统采用前后端分离、逻辑模块化、业务服务与异步任务分离的总体架构。
- 业务服务保持无状态，会话、权限版本、任务状态等共享数据进入统一数据基础设施。
- 文档导入、解析、切片、向量化、FAQ 挖掘和指标聚合必须异步执行。
- 知识检索采用关键词召回与语义召回并行，再进行融合和可选重排。
- 数据权限采用统一策略决策，禁止由各模块自行实现不同口径的鉴权逻辑。
- 所有知识访问均遵循“默认拒绝、先鉴权、后组装上下文”的安全顺序。
- 数据存储分为权威业务数据、检索索引、缓存和对象存储四类，不允许混用职责。
- 部署按接入区、应用区、异步区、数据区和外部依赖区划分，后续可从单机容器演进为集群部署。

## 1. 设计目标与原则

### 1.1 设计目标

- 完整支撑 PRD 中知识维护、AI 问答、FAQ 沉淀和知识缺口闭环。
- 支撑四维数据权限在普通查询、AI 检索、引用预览和 FAQ 发布中的一致执行。
- 支持单篇与批量导入的异步处理、部分成功、失败重试和版本回滚。
- 支持 FAQ 快速应答、关键词与语义混合检索、流式回答和引用溯源。
- 支持模型、搜索、存储和解析能力的替换，不将业务规则绑定到具体供应商。
- 支持指标、日志、链路和审计的端到端追踪。
- 保持演示 MVP 的部署和运维复杂度可控。

### 1.2 设计原则

- 默认拒绝：身份、权限、状态或策略上下文不完整时不得放行。
- 先鉴权后生成：候选知识必须先完成权限过滤，只有授权内容能够进入模型上下文。
- 事实源唯一：业务状态以关系数据为事实源，搜索索引和缓存均可重建。
- 领域隔离：领域规则不依赖数据库、搜索引擎、消息队列或模型 SDK。
- 适配器隔离：外部能力统一通过端口和适配器接入，替换时不修改领域层。
- 异步优先：耗时任务进入任务队列，不阻塞浏览器请求和 API 事务。
- 幂等优先：导入、发布、回滚、缓存装载和任务消费必须可重复执行。
- 最小暴露：未授权知识不得通过标题、正文、引用、得分、日志或错误信息暴露。
- 可观测：跨 API、任务和模型调用传递请求 ID、任务 ID、会话 ID 和用户 ID。
- 可演进：MVP 允许模块化整体部署，接口和模块边界保持未来可拆分性。

### 1.3 架构风格

系统采用“前后端分离 + 模块化业务服务 + 独立异步任务服务”的架构风格。

- 前端：角色化 Web 控制台，负责页面交互和流式结果展示。
- 接入层：统一路由、鉴权前处理、限流、TLS 终止和静态资源交付。
- 业务服务：处理登录、组织、权限、知识、问答、FAQ、缺口、看板和审计。
- 异步服务：处理解析、切片、向量化、FAQ 挖掘、指标聚合和清理。
- 数据基础设施：关系数据库、全文/向量索引、缓存、对象存储和消息队列。
- 外部能力：文档解析服务、生成模型、向量模型和可选重排模型。
- 部署形态：演示阶段允许业务服务整体部署，异步工作进程独立部署；后续按模块或负载拆分。

### 1.4 分层职责

| 层级 | 主要职责 | 禁止事项 |
| --- | --- | --- |
| 展示层 | 页面、表单、会话、状态管理和流式渲染 | 不承担真实权限判断，不保存模型密钥 |
| 接入层 | 路由、限流、请求标识、协议转换和静态资源 | 不实现业务规则和数据权限规则 |
| 应用层 | 用例编排、事务、权限调用、事件发布和 DTO 转换 | 不直接编写查询或索引实现 |
| 领域层 | 聚合、状态机、业务规则和领域服务 | 不依赖具体框架、数据库和供应商 SDK |
| 基础设施层 | 持久化、缓存、检索、消息、对象和模型适配 | 不反向依赖接口层 |
| 异步任务层 | 解析、向量化、挖掘、看板和清理 | 不复制领域规则，不绕过鉴权策略 |

## 2. 模块边界设计

### 2.1 业务模块

| 模块 | 核心职责 | 主要外部依赖 |
| --- | --- | --- |
| 身份认证 | 登录、密码、令牌、会话失效和 SSO 扩展点 | 关系数据、缓存 |
| 组织管理 | 部门树、用户、主部门、角色和账号状态 | 关系数据、缓存 |
| 权限决策 | 菜单/按钮操作权限、四维数据权限、策略决策 | 关系数据、缓存 |
| 知识管理 | 分类、标签、知识单元、版本和生命周期 | 关系数据、对象存储、搜索索引 |
| 文档导入 | 上传、格式校验、解析任务和失败重试 | 对象存储、消息队列、解析服务 |
| 检索服务 | 关键词召回、语义召回、融合、重排和过滤 | 全文/向量索引、模型服务 |
| 问答服务 | 会话、FAQ 缓存、鉴权编排、上下文和流式输出 | 检索、鉴权、模型 |
| FAQ 运营 | 提问聚类、候选、审核、发布和缓存 | 关系数据、缓存、模型服务 |
| 知识缺口 | 缺口识别、聚合、补充草稿和解决闭环 | 关系数据、知识管理 |
| 数据看板 | PV/UV、问题热度、知识热度、Token 和时延 | 关系数据、缓存、检索索引 |
| 审计服务 | 操作审计、问答审计、查询和导出 | 关系数据 |
| 模型适配 | 生成、向量、重排、超时、重试和 Token 统计 | 外部模型服务、关系数据 |

### 2.2 模块依赖规则

- API 层依赖应用服务，不直接访问数据层。
- 应用服务负责调用权限决策并建立事务边界。
- 领域层不得引用具体 ORM、搜索引擎客户端、消息客户端或模型 SDK。
- 基础设施层实现领域接口，不承载业务决策。
- 异步任务通过应用服务执行用例，不直接修改跨模块数据表。
- 跨模块读取优先使用查询服务或明确接口，禁止任意联表穿透模块边界。
- 共享代码只包含通用类型、错误、时钟、ID、日志和配置，不承载业务规则。

### 2.3 无状态与共享状态设计

- 业务 API 实例保持无状态，可水平扩展。
- 登录态使用签名令牌；权限版本和强制失效状态进入共享缓存。
- 会话内容、任务状态、知识状态和 FAQ 以关系数据为事实源。
- SSE 连接状态保留在单个 API 实例，断线重连通过消息序号恢复或重新生成。
- 文件上传先进入对象存储或临时区，不能只保存在应用进程本地磁盘。

### 3.2 AI 鉴权问答流程

<img src="assets/design-selected/03-双路检索与重排链路/jEh54.png" alt="双路检索、RRF 融合与 Reranker 重排图" width="100%">

#### 3.2.1 执行顺序

1. 接收用户问题和会话 ID，校验会话归属与账号状态。
2. 获取用户主部门、角色集合和当前权限版本。
3. 执行 FAQ 标准化匹配与语义匹配，并校验 FAQ 自身权限。
4. FAQ 命中且授权时直接返回标准答案，记录审计并结束。
5. FAQ 未命中时并行执行关键词召回和语义召回。
6. 对候选结果完成去重、融合和可选重排。
7. 调用统一权限决策，将候选分为授权和受限两组。
8. 仅使用授权切片组装上下文，禁止受限内容进入模型输入。
9. 调用生成能力，以 SSE 方式输出回答和引用信息。
10. 回答结束时追加受限提示，并异步写入问答审计和看板事件。

#### 3.2.2 关键输出事件

| 事件 | 说明 | 必需字段 |
| --- | --- | --- |
| `meta` | 会话和模型元信息 | session_id、request_id、permission_version |
| `delta` | 流式文本片段 | content |
| `citation` | 引用知识 | knowledge_id、version_id、title、section、snippet |
| `warning` | 权限或降级提示 | code、message |
| `usage` | Token 和耗时 | prompt_tokens、completion_tokens、latency_ms |
| `done` | 回答完成 | message_id、finish_reason |
| `error` | 失败信息 | code、message、retryable |

#### 3.2.3 关键规则

- 任意阶段身份或权限上下文缺失，按默认拒绝处理。
- 受限知识不得以标题、摘要、引用、得分或错误信息形式返回。
- FAQ 命中不能绕过 FAQ 自身权限。
- 生成失败不得改为通用知识回答。
- SSE 中断后保留已生成内容，重试必须重新执行权限校验。
- 审计记录召回、授权、拦截、Token 和时延，不默认保存完整回答正文。

### 3.3 知识导入与发布流程

1. 接收单文件、多文件或文件夹上传请求。
2. 校验文件扩展名、大小、文件头、哈希和重复情况。
3. 原始文件写入对象存储，任务记录写入关系数据。
4. 向任务队列投递解析任务，支持幂等键和失败重试。
5. 解析服务将输入转换为规范 Markdown，并输出图片资源。
6. 清洗 Markdown，保留标题层级、表格、代码块和来源定位。
7. 按标题、段落和语义边界生成 Chunk，写入元数据。
8. 生成向量表示，并同步写入全文索引和语义索引。
9. 版本文档进入“已索引/待发布”，知识单元默认无数据权限。
10. 管理员配置权限并人工发布，当前版本完成原子切换后进入检索。
11. 失败任务单独重试，不阻塞同一批次其他文件。

### 3.4 FAQ 与知识缺口闭环

1. 问答审计产生问题文本、部门、召回结果和鉴权结果。
2. 周期任务或手动任务执行语义去重与问题聚类。
3. 系统根据来源证据形成权限签名分组。
4. 安全条件满足时自动生成 FAQ，否则进入人工审核。
5. 发布 FAQ 时写入关系数据，并刷新快速应答缓存。
6. 没召回任何候选的问题进入知识缺口。
7. 有候选但全部受限的问题进入权限拦截统计，不进入知识缺口。
8. 有授权切片但置信度不足的问题进入低置信度缺口。
9. 管理员可将缺口转为知识补充草稿，补全发布后自动关闭缺口。

### 3.5 权限变更与会话失效流程

1. 部门、角色、账号状态或知识数据权限发生变更。
2. 权限服务递增受影响用户的权限版本。
3. 共享缓存中的权限版本立即更新。
4. 业务 API 在下一次请求发现令牌版本落后时拒绝请求。
5. 已建立的 SSE 流在下一个检查点终止。
6. 用户重新登录，加载最新部门和角色集合。
7. 审计记录记录变更人、变更对象、前后值和生效时间。

### 3.6 核心状态机

#### 知识单元

`草稿 -> 待发布 -> 已发布 -> 已停用 -> 已归档`

- 只有“已发布且当前版本已索引”的知识参与普通检索。
- 停用后立即退出检索，历史数据保留。
- 归档后只读，不参与编辑和默认检索。

#### 版本文档

`处理中 -> 已索引 -> 当前版本` 或 `处理中 -> 解析失败 -> 重试`

- 历史版本保留但不参与默认检索。
- 回滚必须在新版本或历史版本完成索引后原子切换。

#### FAQ

`候选 -> 待审核 -> 已发布 -> 已停用` 或 `候选 -> 已驳回`

- 发布后缓存生效。
- 更新、停用或权限变化后缓存立即失效。

#### 知识缺口

`待处理 -> 已转草稿 -> 已解决` 或 `待处理 -> 已忽略`

- 关联补充知识发布后，缺口自动解决。
- 草稿删除或驳回后，缺口恢复待处理。

## 4. 数据架构设计

### 4.1 数据域划分

| 数据域 | 权威存储 | 可重建数据 | 主要用途 |
| --- | --- | --- | --- |
| 身份组织 | 关系数据 | 权限缓存 | 用户、部门、角色、账号状态 |
| 权限策略 | 关系数据 | 权限版本缓存 | 菜单、按钮、四维数据权限 |
| 知识资产 | 关系数据 | 搜索索引、预览缓存 | 知识单元、版本、分类、标签 |
| 文档内容 | 对象存储 + 关系元数据 | 索引、缩略图 | 原文件、Markdown、图片 |
| 检索索引 | 全文/向量索引 | 可从知识资产重建 | 关键词、向量、过滤字段 |
| 问答会话 | 关系数据 | 前端短期缓存 | 会话、消息、引用 |
| FAQ | 关系数据 | FAQ 缓存、搜索索引 | 标准问题、答案、权限、状态 |
| 知识缺口 | 关系数据 | 聚合视图 | 缺口、频次、补充关联 |
| 看板指标 | 关系数据 + 聚合结果 | 看板缓存 | PV/UV、Token、时延、热度 |
| 审计 | 关系数据或审计存储 | 无 | 操作与问答审计 |

### 4.2 核心实体关系

- 部门与用户：一个用户属于一个主部门。
- 用户与角色：多对多，一个用户可有多个角色。
- 知识单元与版本：一对多，一个知识单元可有多个版本。
- 版本文档与切片：一对多，版本发布后生成 Chunk。
- 知识单元与权限实体：一对多，支持全局、部门、角色、个人。
- 会话与消息：一对多，每个用户只能访问自己的会话。
- 消息与引用：一对多，引用记录知识、版本、章节和片段定位。
- FAQ 与权限实体：一对多，FAQ 独立配置四维权限。
- 知识缺口与补充草稿：可一对多，全部完成后再关闭缺口。

### 4.3 数据建模约束

- 所有业务实体使用全局唯一 ID，建议采用可排序的 UUID 或等价方案。
- 所有时间字段保存 UTC，展示时按用户时区转换。
- 外键关系必须明确级联规则；知识删除不级联删除审计记录。
- 核心表保留创建人、更新人、创建时间、更新时间和版本号。
- 业务状态使用受控枚举，禁止使用无约束字符串。
- 金额、分数和阈值使用定点数或明确精度字段，禁止浮点误差影响判定。
- 大文本不直接保存在高频列表查询表，按内容域拆分。

### 4.4 检索索引设计

- 每个知识切片至少包含：知识 ID、版本 ID、标题、分类、标签、权限实体、正文、向量、章节定位、状态和更新时间。
- 索引采用版本化命名和只读别名，重建后原子切换别名。
- 权限实体字段只用于过滤候选，不直接返回给普通用户。
- 普通用户检索必须带状态过滤和权限过滤。
- 管理查询可检索停用知识，但必须校验知识管理权限。
- 索引删除采用先停止别名校验、再异步清理的方式，避免删除过程中出现半状态。

### 4.5 缓存设计

| 缓存对象 | 关键字段 | 失效条件 | 失效后果 |
| --- | --- | --- | --- |
| FAQ 缓存 | faq_id、version、question_hash、permission_version | FAQ 更新/停用/权限变化 | 回退正常检索 |
| 权限版本 | user_id、permission_version | 部门/角色/账号/权限变更 | 拒绝或重新加载 |
| 模型配置 | model_type、version | 配置发布或回滚 | 回退旧配置或报错 |
| 看板聚合 | dimension、time_range、dept_id | 新指标聚合完成 | 展示延迟数据 |
| 分布式锁 | resource_type、resource_id | 任务完成或超时 | 防止重复发布与重复索引 |

### 4.6 一致性与事务边界

- 关系数据是业务状态的权威事实源。
- 知识发布先完成版本和权限校验，再提交数据库状态，最后异步刷新索引。
- 索引刷新失败时，知识保持在待发布状态，不对外提供检索。
- 删除知识先使检索和缓存失效，再异步清理对象、索引和正文。
- FAQ 发布先写数据库，再刷新缓存；缓存失败不影响事实状态。
- 异步任务使用幂等键，重复消费不得产生重复版本、重复 FAQ 或重复审计。
- 跨系统操作采用“状态 + 重试 + 补偿”而不是强分布式事务。

## 5. 权限与安全设计

### 5.1 权限模型

系统同时使用两类权限：

- 操作权限：基于角色的菜单、按钮和接口权限。
- 数据权限：知识单元或 FAQ 上的全局、部门、角色、个人四类访问规则。

### 5.2 数据权限判定

```text
allow =
  global_allow
  OR department_match
  OR role_intersection
  OR user_match
```

- 默认结果为拒绝。
- 权限规则按 OR 组合，不实现显式拒绝规则。
- 部门匹配支持“仅本部门”和“包含下级部门”。
- 全局权限只对已登录且状态正常的用户生效。
- FAQ 使用独立权限，不自动继承源知识权限。
- 操作权限通过不代表数据权限通过。

### 5.3 策略决策点设计

- 所有知识访问统一调用策略决策接口。
- 输入：用户上下文、权限版本、资源 ID、资源类型和动作。
- 输出：Allow、Deny、Reason Code 和策略版本。
- 批量检索场景支持批量资源判定，减少逐条查询。
- 决策结果可以短时缓存，但必须绑定用户权限版本。
- 权限服务不可用时返回拒绝，不允许异常放行。

### 5.4 安全边界

- 登录接口必须防止暴力破解、账号枚举和重放。
- 密码使用强哈希算法，密钥和模型凭据加密保存。
- 上传文件执行扩展名、MIME、文件头、大小和恶意内容校验。
- 解析服务与业务服务隔离运行，限制文件系统读写范围。
- 检索内容按不可信输入处理，防止文档中的提示注入。
- SSE 输出不得泄露系统 Prompt、密钥、内部路径或未授权知识。
- 所有导出行为必须记录操作者、范围、时间和结果。
- 日志禁止记录密码、密钥、完整令牌和未授权正文。

## 6. 接口与协议设计

### 6.1 通用接口规范

- 接口风格：以 REST 为主，资源命名使用复数名词。
- 版本前缀：`/api/v1`；不兼容修改必须提升主版本。
- 认证方式：请求携带签名访问令牌，服务端必须校验用户状态和权限版本。
- 数据格式：请求和响应使用 JSON，文件上传使用 multipart。
- 时间格式：ISO 8601 UTC 时间字符串。
- 分页方式：游标分页优先，后台列表可使用页码分页。
- 幂等方式：导入、发布、回滚、FAQ 发布和删除等高危操作支持幂等键。
- 请求追踪：所有请求必须携带或生成 `request_id`，响应头返回相同值。
- 权限模型：接口操作权限与数据权限分别校验，任何一项失败均拒绝。

### 6.2 响应结构

成功响应：

```json
{
  "code": "OK",
  "message": "success",
  "data": {},
  "request_id": "req_xxx"
}
```

失败响应：

```json
{
  "code": "AUTHZ_DENIED",
  "message": "无权访问该资源",
  "details": {},
  "request_id": "req_xxx"
}
```

错误码采用“领域前缀 + 原因”，例如：

- `AUTH_INVALID_CREDENTIALS`
- `AUTH_SESSION_INVALIDATED`
- `AUTHZ_DENIED`
- `KNOWLEDGE_VERSION_NOT_INDEXED`
- `INGEST_PARSE_FAILED`
- `QA_NO_AUTHORIZED_CONTEXT`
- `FAQ_PERMISSION_CONFLICT`
- `MODEL_PROVIDER_TIMEOUT`
- `SYSTEM_RESOURCE_CONFLICT`

### 6.3 API 分组

| 分组 | 路径示例 | 职责 |
| --- | --- | --- |
| 认证 | `/api/v1/auth/*` | 登录、刷新、退出、改密 |
| 用户 | `/api/v1/users/*` | 用户、状态、角色、密码重置 |
| 部门 | `/api/v1/departments/*` | 部门树、成员和下级范围 |
| 角色 | `/api/v1/roles/*` | 角色与菜单/按钮/接口权限 |
| 知识 | `/api/v1/knowledge/*` | 知识、分类、标签、版本、状态 |
| 导入 | `/api/v1/ingestion/*` | 上传、任务、进度、失败重试 |
| 权限 | `/api/v1/permissions/*` | 四维数据权限查询与修改 |
| 问答 | `/api/v1/qa/*` | 会话、消息、SSE、引用 |
| FAQ | `/api/v1/faqs/*` | 候选、审核、发布、缓存 |
| 缺口 | `/api/v1/gaps/*` | 缺口、聚合、补充草稿 |
| 看板 | `/api/v1/analytics/*` | 指标、趋势、排行、导出 |
| 审计 | `/api/v1/audit/*` | 操作审计、问答审计和导出 |
| 模型 | `/api/v1/model-configs/*` | 模型配置、测试和启停 |

### 6.4 SSE 协议约束

- SSE 接口必须使用已认证连接。
- 首事件返回请求 ID、会话 ID、模型和权限版本。
- 文本增量、引用、警告、用量和完成事件必须结构化。
- 客户端断线重连时必须携带最后事件序号。
- 服务端不保证断线后继续同一生成过程，但必须保证已发送内容可恢复展示。
- 服务端应设置心跳事件，避免代理层提前断开。
- 错误事件必须区分可重试和不可重试。

### 6.5 接口兼容规范

- 新增字段默认可选，不破坏旧客户端。
- 删除或重命名字段必须提升 API 主版本。
- 枚举新增值要求客户端具备未知值降级显示能力。
- 接口文档和类型定义必须从同一契约源生成或校验。
- 所有破坏性变更必须记录变更说明和迁移方案。

## 8. 开发与工程规范

### 8.1 命名规范

- 领域实体、表、事件和接口统一使用英文命名。
- 类名使用 PascalCase，函数和变量使用项目统一等价风格。
- 数据库表和字段使用 snake_case。
- API 路径使用小写复数名词和连字符，不使用动词堆叠。
- 事件名称使用 `domain.entity.action` 格式，例如 `knowledge.version.published`。
- 错误码使用大写蛇形，例如 `KNOWLEDGE_VERSION_NOT_INDEXED`。

### 8.2 代码分层规范

- 接口层不得包含业务规则和数据库查询。
- 应用层不得直接拼装底层检索请求。
- 领域层不得导入基础设施客户端。
- 数据访问必须通过仓储或查询服务接口。
- 外部模型必须通过模型适配接口调用。
- 业务时间必须通过统一时钟接口获取，禁止散落调用系统时间。
- 随机数和 ID 生成必须通过统一服务，保证测试可替换。

### 8.3 数据规范

- 所有持久化实体使用全局唯一 ID。
- 时间字段统一保存 UTC，前端按用户时区展示。
- 所有状态字段使用受控枚举并记录状态变更原因。
- 删除知识采用物理清理业务内容、保留审计元数据的规则。
- 重要更新使用乐观锁或版本号避免并发覆盖。
- 迁移脚本必须可重复审计，禁止直接在生产环境手工改表。

### 8.4 API 规范

- 所有接口必须有请求模型、响应模型和错误码定义。
- 所有写接口必须校验权限、幂等性和参数合法性。
- 批量接口必须返回逐项成功/失败结果。
- 列表接口必须定义排序规则和稳定分页游标。
- 大文件不通过 JSON 传输。
- 导出任务异步生成，完成后通过受控链接下载。

### 8.5 测试规范

- 单元测试覆盖领域规则、权限公式和状态机。
- 接口测试覆盖认证、权限、错误码和响应契约。
- 集成测试覆盖关系数据、索引、缓存、对象存储和任务队列。
- 安全测试覆盖越权访问、文件攻击、提示注入和敏感信息泄漏。
- 端到端测试覆盖登录、导入、发布、问答、FAQ 和知识缺口闭环。
- 权限测试必须包含全局、部门、角色、个人和混合命中用例。

### 8.6 日志与异常规范

- 所有异常必须映射为稳定错误码，禁止向用户返回堆栈。
- 日志包含 request_id、user_id、session_id、task_id 和 resource_id。
- 日志级别按 DEBUG、INFO、WARN、ERROR 统一使用。
- 禁止打印密码、令牌、密钥和未授权正文。
- 高风险操作必须写业务审计，不仅依赖普通系统日志。

### 8.7 配置与密钥规范

- 环境配置和代码分离，开发、测试、演示环境使用独立配置。
- 密钥通过安全配置中心、密钥服务或等价机制注入。
- 配置项必须提供类型、默认值、敏感级别和变更影响说明。
- 配置变更需要审计和回滚能力。
- 前端不得保存模型密钥和系统级凭据。

## 9. 部署与运行设计

<img src="assets/design-selected/04-部署拓扑图/Dwq26.png" alt="部署分区图" width="100%">

### 9.1 部署分区

- 接入区：反向代理、静态资源、API 入口和 SSE 长连接。
- 应用区：业务 API、权限决策、知识、问答和运营服务。
- 异步区：消息队列、工作进程、调度器和缓存。
- 数据区：关系数据、全文/向量索引、对象存储和解析服务。
- 外部与观测区：模型服务、监控、日志、追踪和备份。

### 9.2 环境划分

- `dev`：开发联调，使用示例知识和模拟模型。
- `test`：自动化测试，使用隔离数据和固定测试模型。
- `demo`：演示环境，保留完整知识与权限演示数据。
- `prod`：生产环境，启用真实身份、真实模型、备份和高可用策略。

### 9.3 发布顺序

1. 执行数据库迁移和配置校验。
2. 发布无状态业务服务。
3. 发布异步工作进程和调度器。
4. 执行索引兼容性检查。
5. 切换应用版本并验证健康检查。
6. 观察错误率、时延、任务失败率和鉴权拒绝率。
7. 异常时回滚应用版本，不回滚已经完成的业务审计。

### 9.4 备份与恢复

- 关系数据必须定期全量备份并执行增量恢复演练。
- 对象存储必须启用版本或保留策略，防止误删除。
- 搜索索引可重建，不作为唯一备份对象。
- 缓存不参与灾难恢复，恢复后自动重建。
- 模型配置和权限策略必须纳入配置备份。

## 10. 可观测性设计

### 10.1 指标

- API：QPS、错误率、P50/P95/P99 时延、SSE 活跃连接数。
- 鉴权：允许数、拒绝数、策略耗时、权限版本失效次数。
- 检索：关键词召回数、向量召回数、融合耗时、重排耗时、空结果率。
- 模型：请求数、首 Token 时延、完整时延、Token、超时率和重试率。
- 导入：任务队列长度、解析耗时、失败率、重试次数和吞吐量。
- FAQ：候选数、发布数、缓存命中率、缓存失效次数。
- 数据：数据库连接、索引健康、缓存命中、对象存储容量。

### 10.2 日志

- 应用日志、访问日志、任务日志和审计日志分开管理。
- 每条日志必须带 request_id 或 task_id。
- 模型调用日志记录模型、耗时、Token 和状态，不记录密钥。
- 权限拒绝日志记录资源内部 ID 和原因码，不回显受限正文。
- 审计日志与普通运行日志使用不同保留策略。

### 10.3 追踪

- 一个用户问题形成一条跨 API、权限、检索、模型和审计的链路。
- 一个导入任务形成一条跨上传、队列、解析、切片、向量化和索引的链路。
- 追踪数据用于定位慢环节，不用于替代业务审计。
- 采样策略需要兼顾成本和故障定位需要。

## 11. 非功能设计

### 11.1 性能与容量

- 本期不设置硬性性能阻断线，但必须采集首 Token 时延、完整回答时延、检索耗时、解析耗时和 Token。
- 测试报告至少包含 P50、P95、最大值、数据规模、并发数和模型配置。
- 业务 API 必须避免同步执行解析、向量化和批量聚合任务。
- 列表查询必须分页；知识台账和审计日志不得一次性加载全部数据。
- 检索 Top K、重排数量和上下文 Token 上限必须可配置。
- 大文件、批量导入和导出需要任务限流和并发上限。
- 性能瓶颈定位顺序：权限查询 → 检索 → 重排 → 模型生成。

### 11.2 可靠性

- 异步任务必须支持幂等、超时、重试和死信处理。
- 重复消费不能生成重复版本、重复 FAQ、重复索引或重复审计。
- 批量导入允许部分成功，失败项可单独重试。
- 索引切换必须原子执行；失败时继续使用旧版本。
- FAQ 缓存异常时回退正常检索。
- 模型异常时允许重试，不允许改用通用知识回答。
- 权限服务异常时默认拒绝。
- 对象存储、关系数据和配置必须提供恢复机制。

### 11.3 可扩展性

- 无状态业务服务可以水平扩展。
- 异步任务按任务类型拆队列或拆工作进程。
- 搜索索引使用版本化别名，支持离线重建。
- 模型适配层支持新增供应商，不修改问答领域逻辑。
- 权限决策支持新增策略维度，但必须保持统一入口。
- 未来拆分服务时，以当前领域模块为边界，不以数据表为边界。

### 11.4 安全与合规

- 所有知识访问执行服务端权限校验。
- 登录令牌必须支持过期、刷新和强制失效。
- 模型密钥、密码和系统凭据加密存储。
- 用户问题和知识正文按最小必要原则保存。
- 问答审计默认保留 180 天，可配置。
- 删除知识立即停止检索并清理内容，审计元数据继续保留。
- 导出操作必须授权、可审计、可追踪。
- 文件解析服务必须具有资源隔离和只读输入约束。

### 11.5 兼容性

- Web 控制台优先兼容主流现代浏览器。
- Markdown 渲染支持标题、列表、表格、代码块、引用、图片和链接。
- API 契约支持客户端未知字段兼容。
- 文件解析统一输出 UTF-8 Markdown。
- 路径、时间和字符编码处理必须兼容 Windows 与 Linux 部署。

### 12.2 FastAPI 与 Uvicorn 服务模型

- FastAPI 同时承载业务 REST API 和 SSE 问答接口。
- Uvicorn 负责 ASGI 运行；多进程、线程和连接数参数需结合压测确定。
- 业务接口保持无状态，令牌、权限版本和缓存进入 Redis。
- SSE 长连接必须设置心跳、超时、断线检测和最大并发限制。
- 文件上传只负责写入 MinIO 和创建任务，不在 API 请求中执行解析。
- FastAPI 进程不得直接运行 MinerU、VLM、Embedding 或批量向量化任务。
- 同步模型调用不得阻塞 Uvicorn 事件循环，必须使用异步客户端或受控线程池。
- MySQL、Redis、MinIO、Milvus 和模型调用均需独立配置超时与重试。

### 12.3 不使用 Celery 与 RabbitMQ 的异步设计

异步任务使用 MySQL 任务表和独立 Worker，不使用 Celery Worker、Celery Beat 或 RabbitMQ。

#### 12.3.1 任务表建议字段

- `id`：任务 ID。
- `job_type`：解析、VLM、切片、Embedding、FAQ 挖掘、看板聚合、清理。
- `payload`：任务参数 JSON。
- `status`：等待中、执行中、成功、失败、取消。
- `priority`：优先级。
- `run_at`：计划执行时间。
- `locked_by`：Worker 标识。
- `locked_at`：领取时间。
- `heartbeat_at`：长任务心跳时间。
- `attempts`：已尝试次数。
- `max_attempts`：最大重试次数。
- `idempotency_key`：幂等键。
- `last_error`：最近错误摘要。
- `created_at`、`updated_at`：创建和更新时间。

#### 12.3.2 Worker 与调度策略

- 独立 Worker 进程轮询 MySQL 任务表，通过事务锁领取任务。
- MySQL 8.0+ 可使用 `FOR UPDATE SKIP LOCKED` 避免多个 Worker 领取同一任务。
- Worker 处理完成后更新任务状态；失败任务按指数退避更新 `run_at`。
- 超出最大尝试次数的任务进入失败终态，并保留错误信息供人工重试。
- 独立调度进程扫描到期的周期任务，并写入 MySQL 任务表。
- Redis 不保存唯一任务事实，只保存缓存和短期锁。
- 任务表必须按状态、`run_at` 和优先级建立组合索引。
- 已完成任务按保留期归档，避免任务表无限增长。
- 单文件任务失败必须独立于同一批次其他文件。

#### 12.3.3 方案边界

- 该方案减少 RabbitMQ 和 Celery 运维组件，适合演示 MVP 和中小规模部署。
- 高并发和大规模任务场景需压测 MySQL 任务表吞吐、锁竞争和长事务风险。
- 长任务必须发送心跳；心跳超时的任务由清理进程重新置为等待中。
- 不使用数据库轮询实现高频毫秒级任务，延迟要求高的任务需单独评估。

### 12.4 Word/PDF 解析与 VLM 图片摘要

#### 12.4.1 入库步骤

1. 用户上传 Word 或 PDF，FastAPI 校验文件和幂等键。
2. 原始文件写入 MinIO，并写入知识单元和版本文档元数据。
3. 在 MySQL 任务表创建 `parse_document` 任务。
4. 独立 Worker 领取任务并调用线上 MinerU API。
5. 线上 MinerU 将原始文档转换为 Markdown，并抽取图片资源。
6. Markdown、图片和其他附件写入 MinIO。
7. Worker 为每个图片创建 `extract_image_summary` 任务。
8. VLM 提取 OCR 文本、图片描述、实体、表格/图表语义和置信度。
9. 使用 VLM 摘要替换 Markdown 中图片的摘要字段，保留图片对象引用。
10. 按正文、标题层级、表格和图片摘要共同切片。
11. 对切片生成向量和 BM25 文本索引，写入 Milvus。
12. 权限确认并人工发布后，当前版本文档进入检索。

#### 12.4.2 图片摘要替换规则

- Markdown 保留图片引用，不把图片二进制直接写入文本。
- VLM 输出替换图片的 `alt`、Caption 或专用摘要块。
- 切片正文优先使用 VLM 摘要，而不是原始图片文件名。
- VLM 结果保存模型名、版本、提示词版本、置信度和调用时间。
- 低置信度摘要必须标记为待复核，不直接参与公共发布。
- VLM 失败时保留原始摘要或图片说明，不阻塞其他正文切片。
- 图片摘要不得包含模型幻觉的敏感信息，发布前需支持人工复核。

### 12.5 Milvus 检索与双路召回

#### 12.5.1 路线 A：原文混合检索

- 使用原问题执行 BM25 稀疏检索和关键词匹配。
- 对原问题生成 Dense Vector，执行 Milvus 向量检索。
- BM25、关键词和 Dense Vector 候选先做去重和内部融合，形成路线 A 候选集。
- BM25 可用于制度编号、专有名词和精确术语。
- Dense Vector 用于语义相近但字面不同的知识召回。

#### 12.5.2 路线 B：LLM HyDE 检索

- 使用 LangChain 调用 OpenAI 兼容 LLM，生成一个或多个假设性答案或假设文档。
- 对 HyDE 文本生成 Embedding。
- 在 Milvus 中执行 Dense Vector 语义检索。
- HyDE 生成条数、温度、最大长度和超时均可配置。
- HyDE 生成结果必须缓存到 Redis，缓存键包含问题规范化文本、模型版本和参数版本。
- HyDE 失败时允许仅使用路线 A，不阻断问答。

#### 12.5.3 RRF 融合

- 路线 A 和路线 B 的候选结果按排名执行 RRF。
- 默认公式：`score = Σ 1 / (k + rank_i)`，`k` 初始值建议为 60，需实测调整。
- 每个候选保留来源路线、原始排名、融合得分和知识、版本、切片 ID。
- 两路相同切片去重后再参与融合。
- RRF 参数、候选数量和融合权重必须配置化。

#### 12.5.4 Reranker 精排

- 从 RRF 结果中取 Top N 候选进入 Reranker。
- Reranker 对“用户问题 + 候选切片”进行相关性打分。
- 精排后取 Top K 进入权限过滤和上下文组装。
- Reranker 模型、Top N、Top K、批大小和超时待定。
- Reranker 失败时允许回退 RRF 排名，不阻断回答。

#### 12.5.5 鉴权与回答

- 候选知识必须在进入 Reranker 前执行至少一次粗粒度权限过滤，避免未授权内容交给第三方模型。
- Reranker 输出后必须再次执行最终数据权限过滤。
- 只有最终授权切片可以进入 Qwen 上下文。
- FAQ 缓存命中时仍需校验 FAQ 自身权限。
- Qwen 生成通过 SSE 输出，引用卡片记录知识、版本、章节和片段。
- 未授权知识不得通过标题、摘要、得分或错误信息泄漏。

### 12.6 Redis 使用边界

Redis只承担以下职责：

- FAQ 快速应答缓存。
- 权限版本、账号状态和会话失效标记。
- HyDE 结果短期缓存。
- 限流、幂等短期标记和分布式锁。
- 看板高频聚合的短时缓存。

Redis不承担：

- 不保存唯一业务事实。
- 不充当可靠任务队列。
- 不保存完整知识正文。
- 不替代 MySQL 审计与状态机。
- 不允许缓存失效导致权限放行。

### 16.3 登录与会话失效

1. AuthService 通过用户名和密码哈希校验身份。
2. 连续失败达到阈值后锁定账号。
3. 登录成功后签发 HS256 JWT，令牌包含用户 ID 和权限版本。
4. 每次访问根据令牌用户 ID 从 MySQL 重载部门、角色和操作权限。
5. 用户状态、部门、角色或知识权限发生变化时递增权限版本，旧令牌立即失效。
6. 操作权限与数据权限分别校验，拥有菜单权限不代表拥有知识正文权限。

## 17. 关键异常与降级实现补充

### 17.1 统一异常映射

| 异常 | HTTP 状态 | 错误码 | 处理方式 |
| --- | --- | --- | --- |
| ValidationError | 422 | VALIDATION_ERROR | 返回字段或业务校验错误 |
| AuthenticationError | 401 | AUTHENTICATION_FAILED | 登录失败、令牌失效或过期 |
| AuthorizationError | 403 | AUTHORIZATION_DENIED | 操作权限或数据权限拒绝 |
| NotFoundError | 404 | RESOURCE_NOT_FOUND | 目标资源不存在 |
| ConflictError | 409 | RESOURCE_CONFLICT | 唯一约束、部门非空等冲突 |
| DependencyUnavailableError | 503 | DEPENDENCY_UNAVAILABLE | 依赖失败且无法安全降级 |
| SQLAlchemyError | 503 | DEPENDENCY_UNAVAILABLE | 数据库暂时不可用 |

### 17.2 关键降级策略

| 场景 | 降级策略 |
| --- | --- |
| Redis FAQ 不可用 | 跳过缓存，直接查询 MySQL FAQ 事实表 |
| HyDE 生成或 HyDE 检索失败 | 返回空 HyDE 候选并记录警告，继续使用原文混合检索 |
| 原文混合检索异常 | 返回空候选和警告，不允许绕过鉴权使用模型常识回答 |
| Reranker 异常 | 回退使用 RRF 排序并保留 Top K |
| 鉴权引擎异常 | 默认拒绝候选，追加 authorization_unavailable_default_deny 警告 |
| LLM 生成异常 | 返回 DEPENDENCY_UNAVAILABLE，不使用通用知识补答 |
| MinerU/Embedding/Milvus 任务异常 | Worker 标记失败并按任务次数重试，单文件失败不阻塞同批任务 |
| Worker 轮询异常 | 记录异常并继续下一轮，不让进程退出 |
| SSE 流程异常 | 输出 error 事件，包含 code、message 和 retryable |
| Redis 权限缓存异常 | 按权限版本回源 MySQL，权限服务不可用时默认拒绝 |

### 17.3 已实现保障机制
